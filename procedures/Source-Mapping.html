§ 01 · Universal

Required for every balance method.

Source mapping isn't optional anywhere. Cash needs it just as much as Mapping or TIK. The difference is what comes with it — fund mapping is added for the asset-moving methods.

METHOD 01

Cash Conversion

Source mapping only. No fund mapping — building it for cash is a flag the conversion type wasn't confirmed early.

METHOD 02

Mapping

Source mapping + Fund mapping. Both built, both reviewed, both approved before the run.

METHOD 03

Transfer In-Kind

Source mapping + Fund mapping + Re-registration. The fullest pre-work surface of the three.

§ 03 · Review items

Five surfaces to validate.

Validating against the approved source grid means each of these has to line up — names that map, codes that translate, vesting and withdrawal rules that survive the move, and the contribution surface intact.

01

Source names

Each prior-RK source name has a corresponding receiving-plan name. Synonyms aren't acceptable — the cross-walk has to be explicit.

SRC_NM · REPORT_1_NM · REPORT_2_NM
02

Source codes

SRC_I and SRC_TYP_C carry semantics — pre-tax, match, rollover, profit-share, etc. The mapping has to honor each code's behavior.

SRC_I · SRC_TYP_C · SRC_S
03

Vesting provisions

Vesting schedules carry through the move. A source going from cliff to graded would change distribution math — that's a review failure.

vesting schedule per source
04

Withdrawal provisions

Hardship rules, in-service rules, age 59½ rules. Each of these is a per-source flag and has to map to the receiving plan's equivalent.

withdrawal flags per source
05

SCR I

Source-Cost-Reporting indicator — drives compliance reporting downstream. Must be set on every mapped source.

SCR_I
06

Contribution types

Pre-tax · Roth · after-tax · employer match · profit-share · QNEC · QMAC · rollover. Every code has to land in the right bucket.

CONTRIBUTION_TYP_C

§ 05 · Phases

Three steps. Not three days.

Source mapping is fast — but its arrival matters more than its build time. The earlier the cross-walk lands with QA, the more cushion every downstream method has.

Phase · Build

From test files

  • Receive prior-RK test files ASAP from the vendor
  • Pull vendor keys from the test data
  • Cross-walk each source to a receiving-plan source
  • Carry forward vesting / withdrawal / SCR I / contrib type
Phase · Review

Five-surface validation

  • Walk every source row against the approved source grid
  • Flag any source without a receiving-plan equivalent
  • Verify vesting + withdrawal survive the move
  • Check SCR I populated on every row
Phase · Hand-off

Send to QA / TC / TM

  • Send to QA / TC / TM immediately on completion
  • Don't sit on the cross-walk — every day of delay is a downstream day
  • If revision needed, return to build with the QA notes
  • Once approved, hand to Informatica for routing
§ 06 · Touch points

The five things QA looks at.

Names + codes

Each prior source maps explicitly to a receiving source — no synonyms.

Vesting

Schedules carry through. Cliff stays cliff, graded stays graded.

Withdrawal

Hardship · in-service · age 59½ — flags survive the move.

SCR I

Source-cost-reporting indicator on every mapped source row.

Contribution types

Pre-tax · Roth · match · profit-share · QNEC · rollover, all bucketed.

QA approval

Send to QA / TC / TM the moment the cross-walk is done.

§ 07 · SQL

Loan-source build, verbatim.

Internal-conversion takeover loan source query. Joins LOAN_DETAIL_SRC to PLAN_PROV_GRP on ENRL_PROV_GRP_I and a related-group filter, surfaces the open balance per source.

WITH LOAN_DATA AS (
  SELECT B.ACCOUNT_NO, A.SOC_SEC_NO, A.LOAN_NO, A.SRC_I, A.SRC_S, SRC_TYP_C,
         COALESCE(C.ORIG_LN_A, A.ORIG_LN_A) AS ORIG_LN_A
  FROM PENSION.LOAN_DETAIL_SRC A, PENSION.PLAN_SRC_DETAIL D
  JOIN PENSION.PLAN_PROV_GRP B
    ON A.ENRL_PROV_GRP_I = B.ENRL_PROV_GRP_I
    AND B.ACCOUNT_NO LIKE '932339%'
    AND B.RELATED_GRP_TYP_C = 361
  LEFT JOIN PENSION.LOAN_DETAIL_SRC_HISTORY C
    ON C.LOAN_NO = A.LOAN_NO AND C.SRC_I = A.SRC_I
    AND C.SOC_SEC_NO = A.SOC_SEC_NO AND SEQ_NO = 0
  WHERE EXISTS (
    SELECT '' FROM CORP.LOAN_DETAIL C
    WHERE A.LOAN_NO = C.LOAN_NO
      AND C.LN_TR_STAT_CD NOT IN ('4', 'E', '3', '7', '5', '1')
  )
  AND A.SRC_I = D.SRC_I
)
SELECT ' ' AS case_no, ' ' AS sub_id,
       A.SOC_SEC_NO, A.LOAN_NO, A.SRC_TYP_C,
       A.ORIG_LN_A - COALESCE(LN_PRNC_A, 0) AS source_bal,
       SUBSTR(A.ACCOUNT_NO, 1, INSTR(A.ACCOUNT_NO, ' ') - 1) AS old_cont,
       SUBSTR(A.ACCOUNT_NO, 11, 5) AS old_sub_id
FROM LOAN_DATA A
LEFT JOIN (
  SELECT SOC_SEC_NO, LOAN_NO, SRC_S, SRC_I, SUM(LN_PRNC_A) LN_PRNC_A
  FROM PENSION.LOAN_REPAY_SRC
  WHERE LOAN_NO IN (SELECT LOAN_NO FROM LOAN_DATA)
  GROUP BY SOC_SEC_NO, LOAN_NO, SRC_S, SRC_I
) B
  ON A.LOAN_NO = B.LOAN_NO AND A.SRC_I = B.SRC_I AND A.SOC_SEC_NO = B.SOC_SEC_NO
LEFT JOIN PENSION.GET_PLAN_SRC C
  ON A.SRC_I = C.SRC_I;
Get test files early Source mapping waits on the vendor — request prior-RK test files as early as possible, because every other balance-import workstream waits on this cross-walk.
Send to QA the moment it's done Don't sit on a finished cross-walk. Hand it to QA / TC / TM immediately so any revision rounds happen in parallel with the rest of the pre-work, not in sequence.
Don't infer source semantics If a source's vesting or withdrawal rule isn't explicit in the test files, ask the vendor — don't infer from the source name. Misclassifying a single source is a downstream compliance issue.

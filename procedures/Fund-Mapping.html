§ 01 · Where it lives

Two methods, not three.

Fund mapping is the asset-routing crosswalk — it only makes sense when assets are actually moving in kind. Cash conversions don't move assets; they move dollars, then re-buy. Building fund mapping for a cash conversion is the strongest signal the conversion type wasn't confirmed early.

N / A
METHOD 01

Cash Conversion

No fund mapping. Assets are liquidated by the prior RK and arrive as a cash wire — receiving plan re-buys per participant election.

REQUIRED
METHOD 02

Mapping

Source mapping + Fund mapping. Both built from their respective inputs, both reviewed, both approved before the run.

REQUIRED
METHOD 03

Transfer In-Kind

Source mapping + Fund mapping + Re-registration. Re-reg lives inside fund mapping as a per-fund flag.

§ 03 · Review items

Four surfaces to validate.

The TOA tells you what moves and how. The mapping translates that into the receiving plan's fund grid — names line up, tickers line up, CUSIPs line up, and any re-registrations are flagged for the title-only transfer path.

01

Fund codes & names

Each prior-fund line on the TOA matches a receiving-plan fund code. Names should align — a mismatch is a flag, not a typo to fix silently.

FUND_C · FUND_NM
02

Tickers & CUSIPs

Tickers identify the share class — and share class drives fee. CUSIPs are the unambiguous identifier when tickers collide. Both must match the TOA exactly.

TICKER · CUSIP
03

Descriptor codes

Vendor-specific descriptors tell Informatica how to route — domestic equity, intl equity, fixed income, stable value, target-date. One bad descriptor mis-routes a whole fund.

DESCR_C
04

Re-registrations

Some funds change title without a sale — re-registration means the asset comes over as is. Each re-reg fund needs a distinct flag and external setup.

RE_REG_F · custodian setup
§ 04 · Flow

Signed TOA to dev-mode validated.

Linear path with one machine-checked decision: does Informatica developer mode resolve every fund route cleanly? If not, back to mapping with the dev-mode error log.

§ 05 · Phases

Build · validate · sign off.

Three steps, each gated by a different audience. Build is internal. Validate is the machine (Informatica dev mode). Sign-off is human (QA, Trust Counsel, Trust Manager). All three are required; none can be skipped.

Phase · Build

From signed TOA

  • Pull signed TOA from the file — that's the spec, no other source
  • Map each fund line to a receiving-plan fund code
  • Carry ticker, CUSIP, descriptor code exactly
  • Flag any fund flagged for re-registration
Phase · Validate

Informatica dev mode

  • Run the cross-walk through developer mode — every route resolves
  • Resolve descriptor mismatches on the spot
  • Verify re-reg funds route to the title-only path, not the sale path
  • If any route fails, fix and re-run — never wave through
Phase · Sign-off

QA / TC / TM

  • Send the validated cross-walk to QA, TC, TM
  • Pair with the source mapping hand-off — both at once
  • Once approved, the cross-walk is locked for the run
  • Any post-sign-off change requires re-validation
§ 06 · Re-registration

The title-only path.

A re-registered fund doesn't get sold and re-bought — its title transfers from the prior custodian to the receiving custodian, holdings intact. It needs separate setup with the receiving custodian, a 22-day external window, and a hard gate before it can post. Re-reg lives inside fund mapping as a per-fund flag.

RE-REG = N

Standard map

Fund line participates in the normal in-kind transfer — assets move via the run.

RE-REG = Y

Title-only path

Custodian setup with receiving custodian. 22-day external window. Hard gate before posting.

RE-REG = ?

Ask, don't infer

If the TOA is silent on whether a fund re-registers, ask the custodian. Don't infer from name or share class.

§ 07 · Touch points

What QA actually checks.

Fund codes

Each TOA line has a receiving-plan code — explicit, no inference.

Names

Fund names align across the crosswalk — mismatch is a flag.

Tickers

Share-class identifier — drives fee. Match TOA exactly.

CUSIPs

Unambiguous identifier when tickers collide. Always 9 chars.

Descriptors

Vendor route codes — domestic, intl, fixed, stable value, TDF.

Re-reg flags

Per-fund flag. Y means custodian setup + 22-day window + hard gate.

Build from the signed TOA — full stop Don't start fund mapping from a draft TOA, an emailed list, or a screenshot. The signed TOA is the only spec; anything earlier rots when the document is finalized.
Always validate in developer mode A cross-walk that looks right on paper can still fail Informatica's route resolution. Dev-mode validation isn't a formality — it's the test that catches descriptor and CUSIP errors before they become a posting issue.
Don't build fund mapping for a cash conversion If you find yourself building fund mapping for what's labeled a cash conversion, stop and confirm the conversion type. Cash conversions liquidate at the prior RK and arrive as a wire — there's no asset to route, so there's no fund mapping to build.
